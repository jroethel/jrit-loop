# Brief: gate-protocol hardening - the four recurring moves (issue #19)

Date: 2026-09-15.
Tracker: covered by [#19](https://github.com/jroethel/jrit-loop/issues/19) (backlog lane, label `idea`).
Source: the `docs/handoffs/2026-09-15.issue-19-gate-protocol-rulings.md` handoff, itself from the jrit-persona drive run's terminal loop-review (run I13-I23).

## Outcome

The next orchestrator cannot freelance the four moves the current gate protocol does not cover.
Three of the four restore the old loop-stack rule the drive run stepped past; one reorders the flow so the protocol never authors the dirt it then trips on.
Every ruling now points the same direction: restore or protect the invariant, no exception carved.

## Done looks like

`loop-auto/SKILL.md` and `loop-drive/SKILL.md` carry the four amendments below.
A reader of the gate protocol finds each of the four moves explicitly forbidden or required at the point where it is enforced.

## The four resolved rulings

The rulings are settled direction, decided with Jeremy in this session.
Each row names the ruling, the file location where the amendment lands, and the second-order design left for /loop-plan.

## Success criteria

The first three are script-checkable; run them against the amended files.

- Each of the four amendments is present as named text at its home file.
- A grep confirms no surviving license for any of: the journal exempt from the dirty-tree STOP, a live mutate-and-restore probe, precedent substitution for a fresh check, an orchestrator deliverable edit.
- The pre-flight journal-commit step is stated before the dirty-tree STOP in reading order.
- A reader who did not attend this session can tell, from the prose alone, that each of the four moves is settled and which way.

## Seams

The four moves are near-independent edits at four locations, checkable one at a time.
M1 is the only one touching two files in concert: the journal-creation timing in `loop-auto` and the dirty-tree STOP in `loop-drive` must agree, or the commit-before-pre-flight step lands in one file while the STOP it guards sits unreferenced in the other.
M2 may reach a third file: the ringer check-writing ruleset that `loop-drive:161` defers to.

## Approach

Chosen: edit each rule in place at its enforcement home, with no new consolidated section.
Each rule stays where it fires, the diff stays smallest, and the change matches the existing structure of both skills.

Alternative considered: one consolidated "gate-protocol integrity" subsection in `loop-auto/SKILL.md` around lines 41-66, as the original handoff named.
Rejected: it pulls rule text away from the point where the rule is enforced and duplicates prose that already lives at each home, so a future reader has two places to keep in sync.

The handoff's single-file target (`loop-auto/SKILL.md:41-66`) was checked against the files and found incomplete: the dirty-tree STOP (M1), the validator read-only definition (M2), and the attribution rule (M3) all physically live in `loop-drive/SKILL.md`.
The real edit surface spans two skills, and possibly the ringer skill for M2.
