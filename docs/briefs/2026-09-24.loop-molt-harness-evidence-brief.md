# Brief: molt with harness and model evidence

Date: 2026-09-24.
Source session: the Fable status-board prompt study (see `learning_guide.html` in this folder).
Target: `loop-molt` (`~/create/jrit/jrit-loop/skills/loop-molt/`), with a proposed move to jrit-core.
This follows the section shape of jrit-loop's `references/brief-pipeline.md`, so it can go straight to `/loop-plan`.

## Outcome

Every piece of instruction prose Jeremy maintains stays fitted to both the harness that runs it and the model that reads it.
That covers skills, plugins, CLAUDE.md blocks, operating manuals, run-books, and prompts written for other models.
Being fitted means three things.
Nothing repeats or contradicts what the harness already tells the model.
Nothing is left over from an older model.
Nothing is missing that the target model is documented to need.

Presupposition verdict: "molt already covers this" is partly true.
Molt covers harness absorption, judged from memory, and it can only delete.
It misses contradictions inside the artifact, wording problems, conflicts between the artifact and the harness, and additions the target model needs.
Against three real problems found in Jeremy's instruction files during the session, molt as written catches one.

## End artifact

A revised molt protocol, run once on Jeremy's `~/.claude/CLAUDE.md`, `self-manual.md`, and `fable-manual.md`, with a ledger entry recording the harness version and the evidence it used.

## Done looks like

Jeremy runs molt on any instruction artifact and gets findings in four classes, each citing its evidence:
- deletions, because the harness or the model already does it
- conflicts, either inside the artifact or between the artifact and the harness
- rewrites, where the wording fails the wording standard
- additions, where the target model has a documented need the artifact doesn't cover

Each finding cites the harness instruction or model document it rests on, with the version and date of that evidence.
A ledger entry exists after every run.

### D1. Harness evidence (added)

Needed: molt's central question, "would the harness do this unprompted?", is answered today from memory and changelogs.
Step 0 already says "never audit against remembered capability," but it gives no source for what the harness actually instructs.
Molt already probes the harness in one way: the ledger's snapshots record "live probes via current-session tool schemas," which show which tools exist.
They don't show what the harness tells the model.
The change: step 0 names the harness's instruction corpus as the evidence for the plumbing and choreography bins, stamped with the Claude Code version and the date it was indexed.
The evidence must be the prompt set actually running, which means the stock prompts, or the override set if one is applied.
Impact: those verdicts become lookups instead of recall.
It also opens a new class of finding, where an artifact duplicates or contradicts the harness.
Session example: Jeremy's CLAUDE.md says "NEVER auto-add your agent name as co-author," and the harness sends a reminder to add a `Co-Authored-By` line.
His rule wins, but only a check against the harness's text shows the collision.

### D2. Target model (modified)

Needed: the one-line test says "a current frontier model" (`protocol.md:11`).
Whether something is outdated depends on the model reading it.
A line that's redundant for Fable may still be needed on Sonnet, and Jeremy's premium access is ending.
The change: the test names "the target model," taken from the constraint register in step 1.
Step 0 adds the target model's documented behavior as a second source, meaning Anthropic's per-model behavioral-shifts guidance and prompt-audit patterns.
Impact: verdicts hold for the model that will actually run the artifact, not an assumed flagship.

### D3. Direction of change (added)

Needed: every bin either deletes or keeps.
The prompt-audit guidance says an audit's job is "fit, in both directions."
The change: a step 3b checks the artifact against each documented behavior change of the target model.
A gap becomes a proposed addition, tested the same way as a deletion but in reverse: add the text, run a real task, and keep it only if the result improves.
Impact: finds additions like the "don't tidy unrelated things" and "decide minor choices" lines the Fable prompt needed.
Molt can't produce those today.

### D4. Internal consistency (modified)

Needed: step 2 counts duplication (`protocol.md:40`), but two policy blocks that disagree both survive as policy.
The change: step 2 also looks for contradiction.
A conflicting pair goes to the owner as a constraint-register question, which is already an ASK-class gate, and molt never picks a winner itself.
Impact: catches Jeremy's CLAUDE.md conflict between "try to get it fixed" for anything that looks off and "Touch only what you must."
The session's third Fable prompt needed a line to override exactly that conflict.

### D5. Wording standard (added)

Needed: the POLICY action is "keep, sharpen to outcomes" (`protocol.md:47`), and "sharpen" is never defined.
The change: give it a definition that points to one external source rather than restating it.
- Plain volume instead of all-caps emphasis.
- The reason written next to each rule.
- No numeric output caps.
- Positive statements, except where the failure is known to recur.
- Behavioral guidance written as prose, not bullet walls.
- The artifact's prose obeys its own style rules, because a model copies examples.

jrit-core's `ci/banned-tokens.txt` could supply the banned-token part as data.
Impact: catches the self-manual using "load-bearing," a word the global CLAUDE.md bans, and the bare prohibition lists in the second Fable prompt.
Evidence that this is a real gap: molt audited itself on 2026-08-15 (ledger entry `skills/loop-molt/`) and kept the "load-bearing" wording, because wording isn't in any of its bins.

### D6. Ledger entry fields (modified)

The ledger works and lives where it should.
`~/create/loops/loop-stack-session/docs/molt-ledger.md` has 184 lines of entries from 2026-08-15 to 2026-09-13, including molt's audit of itself and the 2026-09-13 loop-drive verdict cited at `loop-drive/SKILL.md:34`.
jrit-loop's `ci/consumer-sweep.sh:9` deliberately flags any `molt-ledger.md` inside the plugin repo as a stray, so ledgers belong in the repo being audited, not in the plugin.
Needed: each entry records the harness snapshot as a Claude Code version plus "live probes via current-session tool schemas."
Once D1 and D2 land, that no longer says which evidence a verdict used.
The change: each entry also records which evidence was used (qmd, grep, shipped excerpt, or memory), the version and index date of the harness corpus, and which model-behavior source was used.
Impact: the next audit can tell a verdict based on a lookup from one based on memory, and can see when the evidence was taken.

### D7. Home (modified): move to jrit-core

Case for moving: molt audits any instruction prose, including jrit-core, personas, CLAUDE.md, other plugins, and Claude Code skills in general.

It already ships `jrit-doctor`, which checks drift in the installed files, and molt checks drift in the instructions, so the two belong together.

## Role of the system prompts

The system prompts are evidence for D1 only.
D4 and D5 need nothing outside the artifact.
D2 and D3 need the model's documented behavior, which is a different corpus.
The system prompts say what the harness tells the model to do.
The model documentation says how the model responds to prose.
Molt needs both, and they differ in size, in how often they change, and in who publishes them.

Harness prompts have converged to one set per Claude Code version, with model-specific sections sent only where models differ.
So molt needs one harness corpus per version, not one per model.

### qmd collection

Pros:
- **Finds paraphrases.** Molt's central question is a paraphrase match, because a skill rarely uses the harness's wording. In the session, the away-summary prompt and the subagent-brief guidance turned up only through semantic queries, while a guessed-keyword search found nothing.
- **Citable results.** Results come with document IDs and line numbers, which suits a ledger.
- **Scales.** Ranked results stay manageable across about 8,800 prompt fragments.

Cons:
- **Local dependency.** It works only where qmd is installed and indexed, which cuts against molt's aim of working on any harness.
- **Staleness.** An index can quietly point at files that no longer exist. In the session, a 33-day-old index cited a folder that had been deleted.
- **Semantic mode needs local models.** Re-indexing changes local state and is the user's call.
- **Plausible near-misses.** Ranking can surface documents that look relevant but aren't.

### grep on a checkout of the prompt catalog

Pros:
- **No dependency.** Nothing to install.
- **Exact and current.** Matches are exact and always reflect the checkout.
- **Reproducible.** The command itself can go in the ledger.

Cons:
- **Misses paraphrase.** That's exactly the case molt cares about most.
- **Needs the terms up front.** You must already know the words to search for.
- **Noisy at this scale.** Most fragments are conditional tool output.

### Files that travel with the skill

Three forms are possible.
- **Curated excerpts.** The small set of harness instructions molt checks against most often, such as plan mode, memory, subagent briefs, doing tasks, and tone.
- **A generated digest.** One file per harness version listing each prompt's name, description, version, and whether it's always sent or conditional.
- **A dated excerpt of the model-behavior guidance.**

Pros:
- **Portable.** They work with no catalog and no index.
- **Reviewable.** Changes show up in git.
- **Survive upstream changes.** The Piebald changelog records that v2.1.251 dropped the Claude API reference suite, which held the model-migration and prompt-audit guidance, from the cataloged Claude Code prompts. A shipped excerpt keeps working either way.

Cons:
- **They go stale.** They must be re-extracted for each version, and the prompt-audit guidance itself lists hardcoded version-specific facts as a way skills decay.
- **Selection bias.** Curated excerpts carry whatever bias went into choosing them.

### Recommendation

- **Harness evidence:** use qmd where it's available and grep on the catalog checkout otherwise. Don't ship the harness corpus with the skill. It's large and changes about monthly, so a shipped copy would go stale fastest.
- **Model evidence:** ship a small, dated excerpt with the skill, because it's short, rarely changes, and may no longer be included in the harness.
- **Ledger:** record which evidence was used, its version, and the date it was indexed.
- **When no corpus exists for the harness:** fall back to memory and mark every verdict that depends on it as unverified.

## Other uses of system-prompt awareness

1. **CLAUDE.md and memory hygiene.** Find lines that repeat what the harness already says, or collide with it, such as the co-author example.
2. **Writing prompts for other models.** `loop-drive` step prompts, ringer manifests, and Fable prompts can be checked against what the worker already receives. For example, the harness's subagent guidance says to "hand over the question" rather than steps.
3. **A third review lens.** `rubix-review` and `loop-review` could add a harness-fit lens alongside the existing ones.
4. **Doctor-triggered molt.** When the Claude Code version changes, `jrit-doctor` could list artifacts whose last ledger entry is from an older version.
5. **Root-causing surprising agent behavior.** Before adding counter-instructions, search the harness for the instruction behind the behavior. Examples include the attribution reminder, the plan-mode rules, and the auto-memory guidance.
6. **Designing features on top of the harness.** Know what already exists before building. The status board is the example, with the away summary, the hook events, and scheduled jobs being session-only.
7. **Persona and voice work.** The harness's tone and length instructions interact with jrit-persona voices, so conflicts should surface before a persona ships.
8. **Self-manual evidence and distillation.** Separate behavior the harness causes from behavior Jeremy causes, so the manual doesn't record rules the harness already enforces.
9. **Auditing override sets.** A rewrite such as lobotomized-claude-code is itself a molt pass on the harness, and its stock-versus-rewrite diffs make good worked examples for calibrating the bins.
10. **Token and cost audits.** Track harness prompt size across versions, next to the existing `token-audit` work.

## Workflows that benefit

- **A Claude Code update or a new model generation.** Run a molt sweep, where the ledger shows which artifacts are behind.
- **Before extending any skill.** Molt's own rule is "never add prose to un-audited prose."
- **Writing any prompt meant for a Claude model.** Check the target model's behavior guidance first. Skipping this is why the session's first Fable prompt fell short.
- **Editing CLAUDE.md or the manuals.** Look for conflicts with the harness and within the file.
- **Briefs from `/loop-plan` and `/loop-drive`.** Check whether they repeat or contradict what the worker already receives from the harness.
- **Self-manual regeneration.** Use the separation described in item 8 above.

## Optional speed-up: Jev for the checks that compare one list against another

Sources: `jev-research/jev-research-brief-2026-09-21.md` and `jev-research/jev-research-addendum-2026-09-23.md`.
Whether Jev helps depends on whether a step compares the artifact against something large, not on how big the audit is.
Every audit, even of a single skill, runs D1 against the roughly 8,800 harness prompts, so D1 benefits from Jev at any size.
Steps confined to the artifact itself (sorting blocks into bins, the wording standard, contradictions within one file) don't benefit for a single skill.
A frontier model reads 50 to 200 blocks in one pass, which is the jev brief's own "when not to use" (Section 7.7).
Those steps benefit from Jev only in stack-wide sweeps, where rules are spread across many files.

The fit test is the four-part check from the jev brief, Appendix B: the answers are known in advance, the volume is high, code acts on the result, and a low-confidence result has somewhere to go.

| Molt part                      | Jev fit  | Reason                                        |
|--------------------------------|----------|-----------------------------------------------|
| D1 block vs harness            | Strong   | qmd finds candidates, Jev picks match or none |
| D4 rule-pair contradictions    | Strong   | Too many pairs for a frontier model           |
| Re-molt after a harness update | Good     | Which changelog items touch which blocks      |
| Step 3 bin sorting             | Moderate | Stack-wide sweeps only, ledger calibrates it  |
| D5 wording standard            | Weak     | grep covers banned words, regex covers caps   |
| D3 model-behavior gap scan     | No       | Few items, each needs judgment                |
| Step 4 subtraction test        | No       | LLM-as-judge, a named anti-pattern (5.2)      |
| Constraint register, premises  | No       | Human decisions and research                  |

**D1** uses the two-stage pattern from the jev brief, Section 7.3.
qmd narrows the roughly 8,800 harness prompts to about 10 candidates per block, and Jev picks the one that already says the same thing, or "none."
The jrit skills total 3,019 non-blank lines, measured 2026-09-24.
At about 2,000 tokens per call, that's about 6M tokens, or roughly $0.25 at Jev's advertised $0.042 per million input tokens.
For a single skill of 200 blocks, the same check is about 400K tokens, or roughly $0.02.
The same 400K tokens on Fable would cost about $4, using the vendor's claim that Jev's input price is 238 times lower than Fable 5.1's.
So for one skill Jev is cheaper and faster, not something a frontier model can't do.
Across the whole stack, the frontier-only cost comes to about $60 per sweep, which is what makes a routine sweep practical only with Jev.

**D4** has to check every pair of rules.
`~/.claude/CLAUDE.md`, `self-manual.md`, and `fable-manual.md` total 370 non-blank lines, which makes about 68,000 pairs.
At 300 to 1,000 tokens per pair, checking every pair costs about $1 to $3.
Across the whole stack there are about 5.7 million pairs, which still comes to about $70 even at 300 tokens each, so a qmd similarity filter runs first.

Conditions:
- **Jev finds candidates, and a frontier model writes the finding.** Molt's findings need reasons, and Jev returns only a pick and a confidence (jev brief Section 5.3). The frontier model explains the matches above the threshold plus a sample from below it.
- **Recall depends on qmd.** Jev "will not surface a note you failed to enumerate as a candidate" (jev brief Section 7.4).
- **Contradictions are its weak spot.** TypeSafe lists "indirect or hinted-at questions" as a weakness, and the CLAUDE.md conflict found this session is exactly that kind. Tune D4 to over-report and let the frontier model reject the extras. Never treat Jev's "no" as a clean bill.
- **Calibration hasn't been tested on this kind of task.** The ledger's past verdicts (184 lines, from 2026-08-15 to 2026-09-13) are the labeled set to check it against before any threshold is trusted.
- **Pin the version, and ask the owner which one.** Thresholds don't carry across releases (addendum item 3), so the pilot pins one model version, logs `r.model` on every call, and records it as an evidence field for D6. Which version to pin is an ASK at pilot time, added to the constraint register, because the research gives different identifiers for different access routes: `jev-1.13.0` in the addendum's two articles, `typesafe/jev-1.13` on OpenRouter, and `typesafe-ai/jev` on Vercel AI Gateway (jev brief Section 2). None of those was checked against the live model list. Never use the `jev-latest` alias. Owner ruling 2026-09-24: decide at pilot time by checking the live model list on the route the pilot uses.
- **Keep it optional.** Jev works through OpenRouter, which helps with the portability constraint. Molt is still meant to work on any harness, so Jev is an optional speed-up like qmd, never a requirement.

Recommended first step: run a shadow-mode pilot on D1, following the jev brief, Appendix B.
Run qmd plus Jev on one skill that has already been molted, such as loop-drive, alongside a frontier-only pass, and compare what each flags.
If they agree closely and Jev catches something the frontier pass missed, extend it to the stack-wide sweep, then to D4.
