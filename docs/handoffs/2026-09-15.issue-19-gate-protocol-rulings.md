## What this is

During the drive run the orchestrator took four moves the gate protocol's letter does not cover.
Each was journaled with a rationale and a reversal path, each is defensible, but the next orchestrator should not have to freelance the same calls.
This handoff records Jeremy's ruling on each, the current rule it touches, and the old loop-stack stance found in `~/repos/loop-stack-session/skills/loop-drive/SKILL.md`.

## The four rulings

### Move 1 - dirty-tree STOP fired on the run's own journal file

The batch-review journal is created "the moment autonomy takes effect" (`loop-auto/SKILL.md:58`), before pre-flight, which dirties the tree the dirty-tree STOP then guards (`:46-47`).
The run ruled its own bookkeeping was not STOP-class dirt and proceeded.

- Current rule: STOP always halts on a dirty tree; no exemption named.
- Old loop-stack stance: no exemption present.
- Ruling: **No exemption - STOP as written.**
  The journal must be committed before pre-flight so the tree is clean; the invariant stays absolute.
- Consequence to encode: add the pre-flight commit of the journal as an explicit step so the STOP never fires on protocol-authored dirt in the first place.

### Move 2 - non-vacuity probe needs mutate-and-restore, validators are read-only

Proving a gate actually fires (not vacuously passes) needs a probe: plant an em dash, show the style gate catches it, restore.
That is a mutation, which the read-only validator definition forbids.

- Current rule: validators are read-only.
- Old loop-stack stance: validators are explicitly read-only (`loop-drive/SKILL.md:161`); no mutation licensed.
- Ruling (leaning, aligned with old stance): **forbid mutation - prove non-vacuity with a committed expected-fail fixture.**
  Keeps validators strictly read-only; the fixture is a file designed to fail, checked in, not a live edit.
- Note: this matches the old stance rather than changing it. The drive run's mutate-and-restore was the deviation.

### Move 3 - gate attribution substituting for a unit's first validation round

A unit's completion report showed a defect class an earlier validator verdict had already established as repaired.
The orchestrator fixed it at the gate on that precedent, skipping the unit's own pre-repair validation round, to save quota.

- Current rule: on a FAIL, attribute before relaunching by re-running the check's steps yourself against the tree (`loop-drive/SKILL.md:190`).
- Old loop-stack stance: same - re-run the check yourself against the tree (`loop-drive/SKILL.md:178`); attribution is earned by re-running, never by citing an earlier verdict.
- Ruling (leaning, restores old stance): **forbid precedent substitution - always run the fresh check.**
  Every unit spends its own validation round; precedent never stands in for a run.
- Note: the drive run's precedent-substitution went beyond what the old stance ever allowed. This ruling restores the rule, it does not add one. It also matches Jeremy's own operating rule "run it, do not trust it."

### Move 4 - de-minimis orchestrator edits to deliverables

Two one-line fixes (a missing resume-pointer clause, a one-line gate hardening) were made by the orchestrator directly rather than relaunching a worker.

- Current rule: continuation delegates work down-tier to workers (`loop-auto/SKILL.md:70-71`); orchestrator editing deliverables is not licensed.
- Old loop-stack stance: orchestrator does spec edits and fixes a wrong check directly, but "Never implements" (`loop-drive/SKILL.md:89`, `:178`).
- Ruling (leaning): **allow one-line deliverable edits, with a mandatory journal entry naming the change and its reversal.**
- Note: this is the only move that softens the old rule rather than restoring it. A one-line deliverable fix is a small implementation, so this carves a narrow, bounded, journaled exception to "never implements." This is the one ruling worth a final confirming nod before it ships.

## Why this is a loop-brainstorm task, not a fresh-worker fix

The four moves are policy design, not mechanical edits.
Three of the four (1, 2, 3) touch invariants Jeremy's own operating manual cares about: trusting the protocol over a fresh run, mutating a worktree, exempting uncommitted content from the dirty-tree guard.
A blind worker handed the issue would pick the convenient answer on each and quietly weaken a safety invariant.
The rulings above resolve the direction, but the brainstorm still owes the second-order design each one implies:
the exact wording of the pre-flight journal-commit step (Move 1), the expected-fail fixture convention and where fixtures live (Move 2), whether "always run the fresh check" needs a quota-death escape valve (Move 3), and the precise size ceiling plus journal schema for the de-minimis allowance (Move 4).
That is divergence-then-convergence work with a real design surface, which is exactly loop-brainstorm's front door: it produces the brief that /loop-plan turns into the `loop-auto/SKILL.md` edits.
