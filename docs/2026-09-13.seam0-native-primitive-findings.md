## Verdicts

- **background-dispatch**: EXISTS - the `Agent` tool spawns subagents to run in the foreground or background, and `SendMessage` addresses a still-running agent by ID or name to resume it or pass it a message - https://code.claude.com/docs/en/sub-agents
- **agent-view**: EXISTS - `claude agents` opens a CLI screen listing every background session as a row you can peek at (Space), reply to, or attach into (Enter), so many independent sessions can be dispatched and monitored from one screen - https://code.claude.com/docs/en/agent-view
- **goal**: EXISTS - `/goal` sets a completion condition, and a small fast model re-evaluates it after every turn until it is met, judged impossible, or an unrecoverable error clears it, and it is a user-invoked slash command (interactively or via `claude -p "/goal ..."`), not a prose-callable API - https://code.claude.com/docs/en/goal
- **loop**: EXISTS - the `/loop` bundled skill re-runs a prompt on a fixed cron interval or a self-paced interval Claude chooses each iteration, for as long as the session stays open, and it is user-invoked only, even when the prompt it repeats is itself another skill - https://code.claude.com/docs/en/scheduled-tasks
- **hooks**: EXISTS - hooks are user-defined shell commands, HTTP endpoints, MCP tool calls, LLM prompts, or subagents that fire automatically at lifecycle events such as `PreToolUse`, `PostToolUse`, and `Stop` - https://code.claude.com/docs/en/hooks
- **auto-memory**: EXISTS - Claude writes its own `user`, `feedback`, `project`, and `reference` notes to a per-repository memory directory indexed by `MEMORY.md`, loaded at the start of every session and distinct from CLAUDE.md, which the user writes - https://code.claude.com/docs/en/memory#auto-memory
- **skill-frontmatter**: PARTIAL - SKILL.md recognizes roughly twenty frontmatter keys (`name`, `description`, `context`, `agent`, `background`, `paths`, `allowed-tools`, `model`, `effort`, and others), but there is no bare `fork` key; forking into a subagent context is written as `context: fork` paired with `agent:` - https://code.claude.com/docs/en/skills
- **plugin-root**: EXISTS - `${CLAUDE_PLUGIN_ROOT}` resolves to the plugin's installation directory for scripts, binaries, and bundled config, and the docs warn it changes on update so nothing should be written to it as durable state - https://code.claude.com/docs/en/plugins-reference
- **validate**: EXISTS - `claude plugin validate <path> [--strict]` validates a plugin manifest and its components, a manifest-less plugin directory (v2.1.233+), or a marketplace directory, and `--strict` promotes unrecognized-field warnings to failures - https://code.claude.com/docs/en/plugins-reference#plugin-validate
- **eval**: EXISTS - `claude plugin eval` runs a plugin's `evals/` suite (`prompt.md` + `graders/*.md`, or `case.yaml`) three times per case by default, scores a with-plugin arm against a no-plugin baseline, and exits nonzero when any case scores below `--threshold` (default 1.0) - https://code.claude.com/docs/en/plugin-evals
- **marketplace**: EXISTS - `.claude-plugin/marketplace.json` declares `name`, `owner`, and a `plugins[]` list, and today's fetch shows each `plugins[]` entry documents `name` and `source` as required plus `description` and an optional `version` as recognized fields - https://code.claude.com/docs/en/plugin-marketplaces
- **agents-md**: DOES-NOT-EXIST - Claude Code reads `CLAUDE.md`, not `AGENTS.md`, and the documented pattern is a `CLAUDE.md` that imports it with `@AGENTS.md` (or a `CLAUDE.md` symlink to `AGENTS.md` on non-Windows hosts) - https://code.claude.com/docs/en/memory#agentsmd

## Discrepancy found: marketplace entry `version` field

The plan's Verified facts table (line 51) states, from a docs fetch also dated 2026-09-13, that `.claude-plugin/marketplace.json` `plugins[]` entries accept `name`, `source`, `description` and **not** `version`, and that `--strict` rejects unrecognized keys.
Today's fetch of the same page, plugin-marketplaces.md, shows a `version` field documented under the plugin entry's optional fields: "If set (here or in `plugin.json`), the plugin is pinned to this string and users only receive updates when it changes."
This is a direct contradiction between two same-day fetches of the same live page, not a stale-memory error on my part; I did not write this verdict from training data.
`marketplace` was not one of the four items this task's step 3 pre-seeded for re-confirmation, so this is a new finding rather than a contradiction of a seeded verdict.
This bears directly on Criterion 7's drift check, which the plan's line 51 says "cannot compare a marketplace entry version" because the field supposedly did not exist; if `version` is in fact a recognized entry field, that reconciliation may no longer be needed and Criterion 7 should be re-examined against the live schema before Task 9 relies on the older claim.
I did not verify which version of the docs the earlier fetch saw, or whether the page changed within the same day; I recommend Task 9 or a human re-run `claude plugin validate --strict` against a marketplace manifest with a versioned entry to settle it empirically rather than trusting either fetch alone.

## What changes if a verdict is wrong

- **background-dispatch**: if the `Agent`/`SendMessage` pairing is thinner in practice than documented, loop-drive's portable core carries more prose-directed baton passing between workers, and the per-harness appendix Task 9 writes shrinks to a smaller set of harness-specific notes; the port still stands either way.
- **agent-view**: if `claude agents` does not behave as documented, loop-drive's guidance for watching parallel workers falls back to prose instructions to poll or check in manually, with no change to the portable core.
- **goal**: if `/goal` turns out to be scriptable from prose after all, Task 9 can drop the "user must type it" caveat from the per-harness appendix, but no task currently depends on that caveat being false, so nothing else changes.
- **loop**: if `/loop` cannot target a skill as its repeated prompt in practice, any drive-loop guidance that suggests `/loop <interval> /skill-name` needs to fall back to a plain repeated natural-language prompt instead.
- **hooks**: if hooks cannot do everything this findings doc implies, any task that planned to use a hook for enforcement should downgrade to a documented instruction in CLAUDE.md or a skill, accepting weaker enforcement.
- **auto-memory**: if auto memory does not behave as documented, tasks that assumed cross-session learning happens automatically must instead write that state explicitly to a repo file, which is already this plan's fallback pattern for durable state.
- **skill-frontmatter**: if `context: fork` and `agent` do not work exactly as documented, every skill in jrit-loop that plans to fork a subagent must be rewritten to spawn via the `Agent` tool from skill body prose instead of frontmatter, which is a larger diff than the frontmatter-only approach.
- **plugin-root**: if `${CLAUDE_PLUGIN_ROOT}` does not resolve as documented, the Global constraint barring it from skill bodies stays correct regardless, since jrit-loop was already designed to avoid it entirely.
- **validate**: if `claude plugin validate` does not distinguish marketplace manifests from plugin manifests as documented, Criterion 1's two-command check (noted in the plan's Verified facts) needs to be re-verified live before Task 2 or Task 9 rely on it.
- **eval**: if `claude plugin eval`'s CI exit codes or `--threshold` behavior differ from this findings doc, Task 10's CI gate needs its exit-code handling re-checked against a live run before it is trusted to fail a build correctly.
- **marketplace**: if the `version` field is not actually accepted on a `plugins[]` entry despite today's fetch, Criterion 7's drift check stays as originally planned with no entry-level version to compare; if it is accepted, as today's fetch indicates, Task 9 gains a real field to diff and should not skip that comparison.
- **agents-md**: if Claude Code ever reads `AGENTS.md` natively in a future version, loop-setup's `CLAUDE.md`-imports-`AGENTS.md` pattern becomes redundant but still harmless, since the import is inert once native support exists.
