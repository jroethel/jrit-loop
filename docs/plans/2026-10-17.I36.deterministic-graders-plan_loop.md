# Orchestration plan: deterministic graders for the eval suite (#36)

## 1. What this file is

This is the loop-drive orchestration plan compiled from `docs/plans/2026-10-17.I36.deterministic-graders-plan.md` (the source plan).
One frontier session, itself a cezar task, executes it as the orchestrator; it never implements, it dispatches, merges, and gates.
The source plan remains the manual fallback: a human can execute it task by task with no loop machinery.
The source plan and its brief `docs/briefs/2026-10-17.I36.deterministic-graders-brief.md` stay ground truth; where this file and the source plan disagree on what a task must produce, the source plan wins and the disagreement is a spec problem for the orchestrator.
Every acceptance check is the source plan's own command string; this file only says who runs it and when.
Autonomy: session override `auto` (repo default `pause`); the source plan's Human checkpoints are STOP class and survive `auto` unchanged.

## 3. Shape, validation layers, and topology

Three validation layers, every unit:

1. Child self-check: the child runs its task's acceptance check and pastes the evidence (jq output, check output) into its final message before `CEZ:DONE`.
2. Per-unit validator: the orchestrator, before merge, audits the child's diff (scope, custody, verbatim graders, sample pairs), then merges and re-runs the plan's acceptance command in `$REPO`.
3. Orchestrator gate: the integration suite (`bash ci/run-all.sh` and `bash tests/plan-review-wiring.sh`) after each merge, plus the W2 combined count before W3 dispatches.

```text
Orchestrator (this cezar task, $BR)  - journal, AGENT STATUS on #36, merges, gate re-runs, asks
 |
 W1  child U1 (sonnet)
 |     gate: audit -> merge -> bite test prints PASS: 20 -> ci/run-all.sh PASS: all
```

## 4. Hazards

1. **Check custody.**
   The gate's check is the plan's acceptance command string, read from `$P`; `docs/plans/` is in no unit's ownership, so no worker can edit it.
   `tests/eval-graders-bite.sh` is U1's deliverable and U4 legitimately appends to it; U2 and U3 must leave it byte-identical, and U4's change must be append-only (section 6.2).
   `tests/plan-review-wiring.sh` is a check file that U2 owns by design (one inserted pair of assertions); the gate confirms the diff is insertions only.
   A child diff touching `docs/plans/`, `ci/`, `.github/`, or `tests/eval-graders-bite.sh` outside the ownership above is a scope violation and a STOP.
2. **Gitignored eval results.**
   `evals/results/` is gitignored, so result JSONs exist only in the child's worktree and never merge.
   The second half of U2's and U3's acceptance checks (the counted-run loop) is re-run by the orchestrator against `<child worktree_path>/evals/results/` before merge when that directory still exists; otherwise the child's pasted jq output is the evidence of record, journaled as not re-run.
   The orchestrator never re-runs an eval at the gate: under D7 that would be a third run.
3. **CEZ environment leaks into eval sessions (deviation).**
   `ringer-absent-degraded` and `resume-pointer-written` drive loop-drive inside the eval; an inherited `CEZ_TASK_ID` would make it take the cezar transport, emit a non-background-agent routing table, or dispatch real cezar tasks.
   Every child runs every `claude plugin eval` with the six `CEZ_*` variables unset (the `ev` wrapper in section 8.1); arguments are unchanged.
   This is an environment change, not a change to what the plan measures; journaled BATCH, reversal "drop the wrapper and rerun the affected cases".
4. **Disjoint child worktrees.**
   U2 and U3 run in separate cezar child worktrees forked from the same committed tip, so neither bite test sees the other's half-written graders (source plan, Dependency graph).
   Merge order is U2 then U3; a merge conflict is a scope violation and a STOP, never resolved quietly.
5. **Resume pointer per unit (deviation from each task's commit command).**
   Each child writes `docs/handoffs/2026-10-17.<unit-slug>.resume.md` after its acceptance check passes and adds it to the plan's closing commit; slugs are `i36-t1-bite-test`, `i36-t2-reply-targets`, `i36-t3-file-targets`, and `i36-t4-kept-llm-gate`.
   The pointer joins each unit's ownership list; it is machine-read, so style rules do not bind it.
6. **Commit attribution.**
   Plain messages only, as the source plan's Global constraints say; every child spec forbids any trailer, overriding any harness attribution reminder, and the orchestrator's own journal and plan commits carry none either.
7. **Long child steps.**
   U2 runs three source runs and six counted runs; if a child's step limit cuts it off, cezar continues the same session (observed for the parent; inferred for children), and the orchestrator keeps polling.
8. **Dirty tree.**
   The journal and this file are committed by pre-flight items 1 and 2; any other uncommitted change is a STOP that autonomy never auto-resolves.`[gate:STOP]`

## 6. Wave loop and gates

### 6.1 Every wave

1. **Dispatch.** Commit `$BR` first (children fork from its committed tip), then per unit:
   `node "$CEZ_BIN" task create "$(cat "$T/U<n>.spec.txt")" --title "I36 U<n>: <unit name>" --kind implement --runner claude --model <model> --success "$(cat "$T/U<n>.success.txt")" --retry-limit 0`
   Never `--budget`, never a `cez` from PATH; at most 4 unfinished children (W2 has two).
   Record the id and branch from the `dispatched <id> on branch <branch>` line and post `gh issue comment 36 --body "AGENT STATUS unit=U<n> child=<id> branch=<branch> worktree=<pending> verdict=running repairs=0"`.
2. **Wait** by ending the turn with the single line `CEZ:MONITORING` once the wave's children are dispatched, as this chain's preflight directs; cezar parks the session and wakes it when a child reports.
   This deviates from the reference's `sleep 60` polling, whose recorded failure was a wake turn ending with no marker; every waiting turn here ends with the marker, so that failure mode does not apply, and no slot or step time burns while U2 runs nine evals.
   On each wake, check every unfinished child once:
   `curl -s "$CEZ_API_URL/api/v1/p/$CEZ_PROJECT_ID/runs/<id>" | jq -r '.status + " " + .createdAt + " " + (.branch // "") + " " + (.error // "")'`
   A child still `queued` about 10 minutes after `createdAt` is surfaced as a question round (child id, status; cancel, rerun, or take the unit back) and never polled again.
   A child that settles without `CEZ:DONE` is read at once: a D7 or D3 stop report goes to the human as a question round; anything else is a failed unit (step 3, repair).
3. **Gate, per child, in merge order (W2: U2 then U3).**
   1. Read the child's final message and structured output; its report is never the verdict.
   2. Scope: `git diff --name-only HEAD...<branch>` lists only the unit's ownership paths plus its resume pointer.`[gate:STOP]`
   3. Custody and per-unit audits (6.2).`[gate:STOP]`
   4. `git merge --no-edit <branch>`; a conflict is a STOP surfaced as a question round.`[gate:STOP]`
   5. Re-run the plan's acceptance command (6.2) and the integration suite in `$REPO`.
   6. On a FAIL, attribute by a fresh re-run of the check's steps; if the work is right and the check wrong, fix the check, journal it, and keep the merge; a verdict from an earlier gate never stands in for this re-run.`[gate:STOP]`
   7. Otherwise undo the merge with `git reset --keep ORIG_HEAD` and send the one repair: `curl -s -X POST "$CEZ_API_URL/api/v1/p/$CEZ_PROJECT_ID/runs/<id>/continue" -H 'content-type: application/json' -d '{"text":"<itemized failure>"}'`, then wait, audit, merge, and re-run again.
      A second failure stops that unit without blocking its sibling; its dependents wait.`[gate:STOP]`
   8. Post `AGENT STATUS unit=U<n> child=<id> branch=<branch> worktree=<worktree_path> verdict=<pass|fail|stopped> repairs=<0|1>` on #36.
4. **Close the wave:** append the gate's journal entries and the wave summary to `$J`, then `git add "$J" && git commit -m "Journal #36: close the W<k> gate"`.
5. **Distill before advancing:** a repeated failure pattern becomes a fix in the next unit's spec block (BATCH when confined to one unit, not changing what it produces, and 15 lines or fewer; STOP otherwise).`[gate:BATCH]`
6. **Advance only on a green `$BR`.**
