# Gate-Protocol Hardening Implementation Plan

> For executors: tasks use checkbox syntax; execute in dependency order; a task is done when its
> acceptance check passes. No specific tooling, harness, or skills are assumed.

**Goal:** Amend `skills/loop-auto/SKILL.md` and `skills/loop-drive/SKILL.md` so the four recurring orchestrator moves (journal tripping the dirty-tree STOP, a live mutate-and-restore non-vacuity probe, precedent substitution for a fresh check, a de-minimis orchestrator deliverable edit) are each forbidden or required at the exact rule where it is enforced.
**Approach:** Edit each rule in place at its enforcement home, with no new consolidated section, so the diff stays smallest and each rule stays where it fires.
Two files change; because both are shared across amendments and each file is single-owner, edits to a given file serialize, while edits to different files may run in parallel.
Each amendment is a prose edit whose acceptance is a grep (or grep pair) against the amended file, so the grep is the check and there is no failing-test code step.

**Tech stack:** Markdown instruction files; POSIX `grep` and shell for the acceptance checks.
**Source brief:** `docs/briefs/2026-09-15.I19.gate-protocol-hardening-brief.md`.

## Verification note

The acceptance checks are prose greps: they assert the forbidding or requiring sentence is present at its rule, keyed to stable substrings of the inserted text.
A grep therefore proves the rule's text landed, not that no differently-worded softening could ever be authored later; that residual is inherent to grep-checking prose and is accepted here.
The plan does not claim a negative grep "confirms no surviving license"; where a banned move is foreclosed, the positive assertion of the forbidding sentence is the guard, not the absence of a specific stray phrase.

## Dependency graph

One task per amendment, serialized only where two tasks share a file:

```
Task 1 (M1, both files)
  |-> Task 2 (M2, loop-drive) --> Task 3 (M3, loop-drive)
  |-> Task 4 (M4, loop-auto)
```

Task 1 edits both files (loop-auto journal timing, loop-drive dirty-tree STOP and pre-flight checklist), so every other task depends on it.
Task 2 and Task 3 both edit `skills/loop-drive/SKILL.md`, so they serialize: Task 1, then Task 2, then Task 3.
Task 4 edits only `skills/loop-auto/SKILL.md`, which Task 2 and Task 3 never touch, so Task 4 depends on Task 1 alone and runs parallel to the Task 2 to Task 3 chain.
Exclusive file ownership is preserved: no two tasks that could run at the same time touch the same file.

## Human checkpoints

After the tasks pass, a human reads the amended passages end to end and confirms two things a grep cannot establish.

Criterion 4 (judgment): "a reader who did not attend this session can tell, from the prose alone, that each of the four moves is settled and which way."
If the reader cannot tell a move is settled from the prose alone, the wording is reopened before the plan is called done.

Criterion 3 (cross-file reading order): "the pre-flight journal-commit step is stated before the dirty-tree STOP in reading order."
The journal-commit step is defined in `skills/loop-auto/SKILL.md` and the dirty-tree STOP lives in `skills/loop-drive/SKILL.md`, so no single-file grep can establish their relative reading order; the M1 check instead asserts, as its scriptable proxy, that loop-auto states the journal is committed before pre-flight runs.
The human confirms the stronger criterion: reading loop-auto then loop-drive, the rule that the journal is already committed is encountered before the STOP that would otherwise trip on it.
This reclassification of criterion 3 from fully-script-checkable (as the brief framed it) to a scripted proxy plus a human confirmation is a deliberate deviation from the brief, recorded here because the two lenses of the plan review showed a same-file line-number compare cannot verify cross-file reading order.
