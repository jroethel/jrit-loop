# Orchestration plan: molt harness-and-model evidence

## 1. What this file is

This is the loop-drive orchestration plan compiled from `docs/plans/2026-09-25.loop-molt-harness-evidence-plan.md` (the source plan).
One frontier session executes it as the orchestrator; it never implements, it gates.
The source plan remains the manual fallback: a human can execute it task by task with no loop machinery.
The source plan, and its brief `docs/briefs/2026-09-24.loop-molt-harness-evidence-brief.md`, stay ground truth; where this file and the source plan disagree on what a task must produce, the source plan wins and the disagreement is a spec problem for the orchestrator.
Every acceptance check is the source plan's own, extracted verbatim at pre-flight; this file only wraps them.
Step 0 (route: multi-wave dependent build; topology lean; substrate probes) was decided by the driving session and is recorded in the gate journal entries 1 to 5.
Autonomy: session override `auto`; the source plan's Human checkpoints H1 to H6 are ASK or STOP class and survive `auto` unchanged.

Shorthand used throughout, all absolute so every command runs from anywhere:

```bash
REPO=/home/jjrdar/repos/jrit/jrit-loop
P=$REPO/docs/plans/2026-09-25.loop-molt-harness-evidence-plan.md
W=/home/jjrdar/.ringer/work/molt-harness-evidence      # ringer workdir: checks/, expected/, patches/, results/, logs/

RINGER=/home/jjrdar/repos/ringer
BR=loop/molt-harness-evidence                            # integration branch, checked out in $REPO itself
```

The receipt helper is always invoked as `bash "$R" <verb> ...` with the working directory at `$REPO` (it reads the caller's `docs/loop/pointer.md`), never by its execute bit.

Transport and packing decisions:

- Every implementer takes the ringer transport, because none needs in-session tools or mid-flight continuation once the human checkpoints are hoisted to the orchestrator (Step 2's derivation rule).
- Background-agent transport is used only for validators, which need to run in the main checkout against an applied patch and return a structured verdict.
- The D1 to D6 chain packs as six sequential one-task ringer waves (W2a to W2f), not one worker.
  Reasons: the source plan makes each change separately rejectable with its own check and its own commit; a ringer worker cannot commit, so one worker would return one merged patch and D1's check could never be shown to pass at D1's own state; relaunch-never-resume would redo all six changes after a death at D5; and a validator reading one change's diff against one contract's "must not say" list is sharper than one reading six.
  Alternative considered: one background sonnet worker making six commits in its own worktree; rejected because it leaves the claude-zai lane for Anthropic quota and still packs six rejectable changes into one relaunch unit.
- U11F (the Task 11 fixture file) moves from wave 4 to wave 1 because it has no dependency, touches a disjoint path, and shrinks the later fresh-session wave to the audit alone (fewer, fatter waves).
- The verbatim writes the source plan assigns to "the executor" (ledger header, fixture freeze, notes downloads, owner-answer transcription, owner-acceptance section) go to haiku clerk tasks, because the loop-auto continuation rule bars the orchestrator from editing any deliverable itself.
- U12B is the single exception: the orchestrator runs the source plan's verbatim Step 10 and Step 11 script itself, as a background shell.
  Reason: it is a pre-registered, judgment-free experiment script whose only products are the subject model's outputs; a model worker in the middle adds a blinding and gaming surface, cannot hold a 40-minute to 2-hour loop inside one tool call, and would alter the plan's exact invocation.
  This departs from the ringer skill's "if it calls a model, it runs under Ringer" rule and is flagged for the pin review; the alternative is a haiku background worker that launches the same script detached and polls for a done marker.
- herdr is present but unused: the user's herdr skill fires only when herdr is explicitly requested, and ringer's raw logs plus Ringside already give watchability.

## 3. Orchestration shape, validation layers, and topology

Three validation layers, every unit:

1. Implementer self-check: every ringer spec embeds the unit's acceptance check, and the worker runs it before writing its resume pointer and result file.
2. Per-unit validator: the ringer-executed check (the source plan's check wrapped with custody and scope assertions, section 8), plus a background opus validator wherever the check cannot express the judgment (D1 to D6 "must not say" lists and prose rules; the fresh-session reports; U12A's experiment design; U14).
3. Orchestrator gate: a fresh re-run of the source plan's check against the integration tree after the patch is applied, the full suite, and the gate checklist in section 6.

Full suite at every gate (never `ci/run-all.sh`, whose strict plugin validation already fails on the untouched tree per the plan's Parking lot, and never `tests/receipt-gates.sh`):

```bash
suite() { local rc=0 c; cd "$REPO" || return 1
  for c in ci/structure-check.sh ci/consumer-sweep.sh ci/budget-check.sh ci/version-drift.sh ci/secrets-scan.sh \
           tests/pre-plugin-detection.sh tests/local-mode-grammar.sh tests/single-resolution-cases.sh; do
    bash "$c" >/dev/null 2>&1 || { echo "SUITE FAIL $c"; rc=1; }
  done; return $rc; }
```

`ci/consumer-sweep.sh` fails on the untouched tree (baseline, fixed by U01); until U01 is committed at the W1 gate, that one line of the suite is expected to fail and nothing else may.

## 4. Hazard mitigations

Each item says which transport it covers, and is marked **Deviation** where it changes what the source plan says.

1. **Check custody (both transports).**
   Every acceptance check is extracted verbatim from the source plan into `$W/checks/<key>.plan.sh` at pre-flight, wrapped by an orchestrator-owned `$W/checks/<key>.sh`, and both files' sha256 sums are written into the gate journal before wave 1.
   The orchestrator re-verifies them with `sha256sum -c` at every gate; a mismatch is a STOP.
   No worker owns any file under `ci/`, `tests/*.sh`, `docs/plans/`, `ci/reference-allowlist.txt`, `ci/banned-tokens.txt`, or `$W/checks/`, and each worktree check's scope assertion fails any diff that touches them.
   The Check B allowlist and the banned-token list are the two most tempting gaming targets in this run (every D unit's check runs `ci/structure-check.sh`), so both are named explicitly in every D spec.
   Task 1 is not a custody violation: `ci/consumer-sweep.sh` is U01's deliverable by design, and U01's acceptance check is the source plan's subshell, which lives in the plan and in `$W/checks/`, never in a file U01 owns.
2. **Out-of-repo writes are not covered by any worktree isolation (both transports).**
   U02 and G02 write `~/.config/jrit` (itself a git repo with a private GitHub remote); K10, U10, U11, U12A, U12B, U12C, U12E, K13, U13, KH2, and KH4 write under `~/.config/jrit/molt/`; U12E and the kanban commit write `~/repos/kanban/docs/molt-ledger.md`.
   Mitigations: pre-flight records `git -C ~/.config/jrit rev-parse --short HEAD` (d82bf9a at compile) and `git -C ~/repos/kanban status --porcelain` (clean at compile, no `docs/`); every out-of-repo spec is idempotent (append only if absent, overwrite downloads); every out-of-repo check asserts the foreign repo's HEAD and status; no unit pushes any repo.
3. **The main checkout is the fresh sessions' read surface (ringer, non-worktree units).**
   The fresh-session brief names absolute paths under `$REPO/skills/loop-molt/`, so the integration branch `$BR` is checked out in `$REPO` itself, not in a separate worktree.
   Rule: while U10, U11, U12A, or U13 is running, `$REPO` holds no applied-but-uncommitted patch, and the orchestrator only commits resume pointers and journal appends there.
   **Deviation:** the source plan commits on the current branch; this run commits on `$BR` and asks before merging to main (section 6).
4. **Private-content boundary (both transports).**
   Dated copies of `~/.claude/CLAUDE.md`, `~/.claude/self-manual.md`, and `~/.claude/fable-manual.md`, the Task 13 report, its pre-H2 snapshot, and the owner's H1 and H2 answers for Task 13 live only under `~/.config/jrit/molt/` (git-ignored by U02).
   The gate journal, resume pointers, AGENT STATUS receipts, MODEL-NOTES lines, and commit messages record paths and counts for Task 13, never quoted content; validator notes that quote private text stay in the conversation.
   No unit reading private or kanban content takes the claude-zai lane (section 2 footnotes).
5. **Append-only ledgers (ringer, fresh-session units).**
   U10, U11, and U13 append to `~/.config/jrit/molt/molt-ledger.md`, which is appended and never rewritten, so each runs with `max_attempts: 1`; a failed fresh-session unit is a STOP, never an automatic relaunch that would append a second entry.
   Order is enforced by the waves: U10 creates the entries after K10's header, U11 follows the U10 gate, U13 follows the U11 gate.
6. **Blindness of the fresh sessions, source plan ruling 10 (ringer, U10, U11, U13).**
   The ringer spec is the source plan's fresh-session brief with its fields filled and nothing else; the task runs with `worktrees: false`, so its working directory is the ringer task directory under `$W`, outside the repository.
   Retries are off, because a ringer retry injects the check's failure output, and these checks contain the known answers.
   At the gate the validator greps the raw worker log for `docs/plans` and `loop-molt-harness-evidence-plan`; any hit is a STOP, since the run is contaminated.
   **Deviation (forced by ruling 10):** the brief carries no global-rules block, no reviewer conduct contract, and no resume-pointer instruction; the protocol itself carries the U+2014 quoting rule after D6.
7. **Experiment integrity, Task 12 (orchestrator script and ringer).**
   The checklist sha256 is recorded in the report before any run and re-verified at the U12A gate, before H6, and at the C4 check.
   The orchestrator never prints `mapping.tsv` before the U12D join; U12B's own check prints output ids only.
   The scorer works on a scratch copy of `blind/` at `$W/score/`, and the gate greps its raw log for `mapping.tsv`, `prompt-arm`, and `molt-fable5-kanban.md`; any hit is a STOP.
   No run is added after the first run starts, and nothing is re-run to chase a pass (H3).
   U12A may not open any file in `~/repos/kanban/` except through the extraction command.
   **Deviation:** the source plan forbids the companion files only until Step 6's proposals exist, and its list omits `fable5_kanban_noskills.md` and `fable5_kanban_qmd.md`, which exist on this host; this run forbids all of them for the whole unit.
8. **Ringer worktree footguns (ringer, worktree units).**
   Passing worktrees are deleted, so each worktree check exports `git diff --cached HEAD` to `$W/patches/<key>.patch` before asserting anything.
   Specs never instruct a commit (ringer lint hard-blocks it); workers leave changes uncommitted, and the orchestrator applies, reviews, and commits.
   No in-repo deliverable of this run is gitignored; the dry run confirms it with `git check-ignore` on each owned path.
   Ringer's check ceiling is a hard-coded 60 seconds (`CHECK_TIMEOUT_S`), so no ringer check runs the full suite; each runs only its plan check (about 2 seconds, dominated by `ci/structure-check.sh`, measured at 1.8 s).
   Checks run in the task directory: worktree checks `cd "$(git rev-parse --show-toplevel)"` (the worktree), and non-worktree checks `cd "$REPO"` explicitly; mixing the two would test the wrong tree.
   Ringer's check shell is `/bin/sh`, and the plan checks use bash features, so every check is invoked as `bash <file>`.
9. **Harness background-agent hazards (background-agent, validators only).**
   Nested repos: none; no unit uses the harness's own worktree isolation, and ringer worktrees are made from the named `repo` path.
   Per-worktree environments: none; every check is bash and git with no virtualenv.
   Shared append-only files: the fallback ledger (serialized as in item 5), the gate journal and the ringer repo's MODEL-NOTES (orchestrator only), and the ringer logs (per task already); no one-file-per-unit conversion is needed, so there is no deviation here.
   Dirty working tree: the journal and this file are committed by pre-flight items 1 and 2; any other uncommitted change is a STOP that autonomy never auto-resolves.`[gate:STOP]`
   Disjoint files: W1's four units own `ci/consumer-sweep.sh`, `~/.config/jrit/.gitignore` plus `molt/model-notes/`, `skills/loop-molt/references/evidence.md`, and `tests/fixtures/molt/restated-harness/fixture.md`; U11 and U12A write different run files and only U11 touches the fallback ledger; U13 and the Task 12 chain write different ledgers; a merge conflict at any gate is a scope violation.
10. **Commit ownership (both transports).**
    **Deviation:** the source plan's per-task commit commands are run by the orchestrator at the gate, verbatim, with the unit's resume pointer added to the same commit; messages stay plain, one imperative line, with no co-author or attribution line.
11. **Resume pointers for non-worktree units.**
    **Deviation from loop-drive Step 5 (worker writes its pointer):** units with no worktree (K10, U10, U11, U12A to U12E, K13, U13, KH2, KH4, U14) cannot commit into `$REPO` without dirtying the fresh sessions' read surface, and ruling 10 bars adding the instruction to the fresh-session brief, so the orchestrator writes one pointer per source-plan task (`docs/handoffs/YYYY-MM-DD.t10-molt-on-molt.resume.md`, `.t11-fixture-run`, `.t12-kanban-gap-scan`, `.t13-instruction-files`, `.t14-final`) at each of that task's gates and commits it with the gate commit.
    Pointers list out-of-repo artifacts as `~/` paths and never quote their content.
    The source plan's "No commit" steps for Tasks 10, 12, 13, and 14 still hold for the task's own files; only the pointer commits into `$REPO`.
12. **One sentence per physical line on pre-existing text.**
    The global constraint says every edited Markdown file obeys it, but `skills/loop-molt/references/protocol.md` already has multi-sentence lines (lines 30 and 85 at compile).
    Compiled reading, the conservative one: every line a worker adds or rewrites obeys the rule, and untouched pre-existing lines are not reflowed, because each D unit owns only named sections.
    This is flagged to the orchestrator as a spec question (section 6, open rulings).
13. **Nested `claude -p` inside the orchestrator's session (U12B).**
    The Fable runs inherit the host's user-level instructions and hooks (including the ringer nudge hooks) and the parent session's environment; the plan records user-level instructions as a known confound held equal across arms, and this run extends that record to hooks and environment.
    Whether a nested `claude -p` behaves identically to a top-level one is unverified; the U12B check rejects any output under 1000 bytes as a likely error message rather than a design answer.
14. **Fresh sessions load the user's global instructions.**
    U13's auditor runs with `~/.claude/CLAUDE.md` loaded while auditing a copy of that same file; this confound is not removable without changing the plan, and the Task 13 report's risk notes should name it.

## 5. Pre-flight checklist

## 6. Wave loop and gates

### 6.1 The loop, every wave

1. **Launch.**
   Build the wave's manifest from the section 8 templates, with `run_name` `molt-harness-evidence` on every wave, then `cd "$RINGER" && ./ringer.py lint "$W/<wave>.json" && ./ringer.py run "$W/<wave>.json"`.
   Post `AGENT STATUS unit=<U> branch=$BR worktree=<ringer task dir or none> verdict=running repairs=0` on ticket `$N` for each unit launched (the `unit=` field is added because one run ticket carries every unit).
   Ringer's built-in single retry is the repair pass for worktree units (`max_attempts: 2`); non-worktree units that append to a ledger or carry known answers in their check run with `max_attempts: 1`.
2. **Gate.**
   1. Read the run JSON in `~/.ringer/runs/`, which is truth over any shell exit status; read every retried or failed worker log in `$W/logs/`; spot-check at least one passing artifact.
   2. Re-verify custody: `(cd "$W" && sha256sum -c --quiet checks.sha256)`; a mismatch is a STOP.`[gate:STOP]`
   3. For worktree units: `git apply --index "$W/patches/<key>.patch"` in `$REPO`, then re-run the plan check fresh from `$REPO` (`bash "$W/checks/<key>.plan.sh"`), then run `suite`.
   4. Dispatch the unit's background validator where section 2 lists one (templates in section 8.6); on `fail`, reset the applied patch (`git restore --staged --worktree -- <owned paths>` and remove the pointer file), and the unit is stopped.
   5. On pass, commit with the source plan's message verbatim, adding the resume pointer: `git commit -m "<plan's message>"` after `git add <owned paths> <pointer>`; parallel units commit one at a time.
   6. On a FAIL, attribute before relaunching: re-run the check's steps yourself against the tree; if the worker was right and the check was wrong, fix the check (a check is not a deliverable), commit the audited work, and journal the check-bug attribution plus a ringer amendment; a verdict from an earlier gate never stands in for this re-run.`[gate:STOP]`
   7. Resolve stopped units under the slip rules (6.3).
   8. Post `AGENT STATUS unit=<U> branch=$BR worktree=<path or none> verdict=<pass|fail|spec-problem> repairs=<n>` for each unit.
   9. Append the gate's journal entries and write the wave summary into the journal; commit the journal append with the gate commit.
3. **Distill before advancing.**
   Turn any repeated failure pattern from this wave's verdicts into a fix in the next unit's spec template before launching it; a fix confined to one unit, not changing what it produces, and 15 lines or fewer auto-takes as BATCH.`[gate:BATCH]`
   Add one dated MODEL-NOTES line per (model, task_type) per wave to `$RINGER/docs/MODEL-NOTES.md` for the background opus validators, plus one line per signal event (a pin, a re-route, a check-bug attribution, an off-nominal result), supported only by verdicts and diffs; commit it before advancing: `git -C "$RINGER" add docs/MODEL-NOTES.md && git -C "$RINGER" commit -m "MODEL-NOTES: molt harness-evidence wave <w>"`.
4. **Advance only when `suite` is green on `$BR`** (with the one pre-U01 exception noted in section 3).

Runtime re-route: a unit that fails validation twice is re-routed at the gate by the routing chain, usually a pin to opus on the claude engine, with the reason journaled; this is not an automatic ladder.

## 7. Quota and resume

The orchestrator is the loop: if this session dies, nothing advances, and background validators are not a durable scheduler.
The loop is built to die safely at any moment.

Durable state, in the order a fresh session trusts it:

1. Git: `$BR` in `$REPO` (every committed unit), `~/.config/jrit` (the G02 commit), `~/repos/kanban` (the ledger commit), and `$RINGER/docs/MODEL-NOTES.md`.
2. Out-of-repo artifacts, whose presence the plan checks test directly: `~/.config/jrit/molt/model-notes/*.md`, `~/.config/jrit/molt/molt-ledger.md`, `~/.config/jrit/molt/runs/*.md` and `runs/<d>.molt-fable5-kanban/`, `~/.config/jrit/molt/fixtures/<d>/`, and `~/repos/kanban/docs/molt-ledger.md`.
3. Ringer state: run JSON in `~/.ringer/runs/` for `run_name` `molt-harness-evidence`, raw logs and patches and results under `$W`.
4. The run ticket `$N`: its `AGENT STATUS` receipts (unit, branch, worktree, verdict, repairs).
5. Resume pointers: the newest `docs/handoffs/*.resume.md` naming a unit of this run.
6. The gate journal `$J`: every decision and every recorded human answer (Task 13's answers by path).

A session-local cache (such as the validator agent ids used to route a repair message) is convenience only.

Reconciliation procedure (relaunch, never resume):

1. Read the newest resume pointer for this run, then the `AGENT STATUS` receipts on `$N` (`bash "$R" next-eligible <session-id>` surfaces a stale `agent:working` ticket; re-take it with `bash "$R" claim "$N" <session-id> --reclaim`), then `git log --oneline "$BASE".."$BR"`.
2. Check `$RINGER` for an uncommitted MODEL-NOTES line owed by the last gate, and commit it first.
3. Find the first unit whose gate is not closed; git and the files win over any receipt or pointer when they disagree.
4. Worktree units (U01 to U09, U02 included): discard any applied-uncommitted patch in `$REPO` (`git restore --staged --worktree -- <owned paths>`) and relaunch the unit from scratch with its ringer task.
5. Units with append-only or experiment state are not relaunched blindly:

   - U12A: safe to relaunch while `mapping.tsv` does not exist (its spec overwrites every file it owns).

6. Never re-ask a human checkpoint whose answer is already recorded; answers are data, carried forward.
