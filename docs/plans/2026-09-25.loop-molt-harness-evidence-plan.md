# Molt Harness-and-Model Evidence Implementation Plan

> For executors: tasks use checkbox syntax; execute in dependency order; a task is done when its acceptance check passes.
> No specific tooling, harness, or skills are assumed; every step is a file edit, a shell command, a question to the owner, or a hand-off to a fresh session described by its inputs.

**Goal:** Revise the molt protocol (`skills/loop-molt/references/protocol.md` and its wrapper `skills/loop-molt/SKILL.md`) so every verdict rests on dated harness and model evidence, the audit finds conflicts, rewrites, and additions as well as deletions, and every run leaves a ledger entry naming its evidence; then prove it with four real runs.
**Approach:** Ship the evidence-matrix reference first, then land the six protocol changes D1 to D6 as six serialized tasks (each is one change a reviewer can reject on its own, and all six share the same two files), then run the revised protocol four times (molt on molt, a synthetic test fixture, the Fable 5 kanban prompt, and dated copies of the owner's three instruction files), each run producing a findings report and a ledger entry that its acceptance check greps.
Protocol edits are prose, so their acceptance is a grep for anchor phrases scoped to the edited section plus a clean `bash ci/structure-check.sh`; run tasks are accepted by greps and recomputations over the files they produce.
The shipped protocol stays portable: it names upstream evidence sources by URL, and every host path and host command lives in one labeled block of SKILL.md.
**Tech stack:** Markdown instruction files; bash, POSIX grep, GNU awk, git, curl, sha256sum, shuf, mktemp; the prompt catalog checkout at `~/repos/claude-code-system-prompts` (upstream `https://github.com/Piebald-AI/claude-code-system-prompts`); optionally qmd 2.8.3 (collection `piebald-ai`); the `claude` CLI only to read its version and, in Task 12, to run the kanban prompt on the target model.
**Source brief:** `docs/briefs/2026-09-24.loop-molt-harness-evidence-brief.md`, with its companion `docs/briefs/2026-09-25.molt-evidence-matrix-reference.md`.

## Human checkpoints

The executor stops and asks the owner at each of these, and does not proceed past it without an answer.

- **H1 - Constraint register, every run except Task 11.**
  Protocol step 1 is an ASK-class gate: before the fresh session for Task 10 or Task 13 is started, and before Task 12's audit, the executor presents the constraint-register questions (which design choices are deliberate standing constraints, and which model or models will read the artifact) and records the owner's answers verbatim; they go into the fresh-session brief and the findings report.
  For Task 10 the starting list is the register inherited in the prior ledger's 2026-09-13 entry; for Task 12 the target model is already `claude-fable-5-1` (ruling 4) and only the constraints are asked.
- **H2 - Contradictions, one question set per run.**
  Every conflicting pair a run finds (inside an artifact, across the audited files, or between an artifact and the harness where the harness text does not defer to the user) is written into the report's `## Conflicts` section as an `Owner question:` line while the findings are drafted.
  Once the draft exists, the executor presents all of that run's questions to the owner as one question set and writes each answer below its question as an `Owner answer:` line.
  Molt never picks a winner, and the executor never answers on the owner's behalf.
- **H3 - Kanban scores, always shown.**
  After Task 12's blinded scoring and the mapping join, the executor shows the owner the full per-run scores table and both arm means for every tested addition, whether or not anything was kept.
  If nothing is kept, the executor stops there and reports; it never rewrites the checklist, changes the keep rule, or adds runs after the runs have started to chase a pass.
- **H4 - Findings worth reading (the brief's `[judgment]` criterion).**
  After Task 13, the owner reads its findings report and marks each finding accepted or rejected.
  The executor appends a `## Owner acceptance` section to that report stating "Accepted N of M" with the per-finding marks.
  This is a signal only: acceptance is not correctness, so no threshold passes or fails the plan.
  At the same checkpoint the owner has Task 12's scores table in front of them (from H3) and decides whether to apply Task 12's kept addition to the prompt in `~/repos/kanban/fable5_kanban.md` and whether to hand Task 13's generator-routed findings to the self-manual distill pipeline; applying either is outside this plan.
- **H5 - What enters the `~/.config/jrit` repo (a STOP inside Task 2).**
  Before Task 2 commits anything to `~/.config/jrit`, the executor shows the owner the `.gitignore` diff (fixtures, runs, and the fallback ledger ignored; model notes not ignored) and waits.
  The owner approves the commit and decides what, if anything, to un-ignore; an un-ignore is applied as its own later commit after Task 2's check passes, and nothing in this plan commits files under `molt/`.
- **H6 - Kanban run budget (ASK, before any model run in Task 12).**
  Before the first arm runs, the executor states the planned run count (three arm A runs plus three runs per addition under test, at most twelve, plus one scoring session) and a rough estimate labeled as a guess: about 50K to 150K tokens and 3 to 10 minutes per run at high effort, so roughly 0.6M to 1.8M tokens and 40 minutes to 2 hours for twelve runs.
  The executor waits for approval and may run fewer additions if the owner caps the budget, recording the cap in the report.

## How to run

Run every command from the repository root `/home/jjrdar/repos/jrit/jrit-loop` in bash; repo paths below are repo-relative, and paths outside the repo are written with `~/`.
Each acceptance check is one shell command (often a parenthesized subshell) that prints a `-OK` token and exits 0 when the task is done.
Protocol edits are specified by contract: the exact anchor phrases the check greps must appear verbatim in the named section, and the surrounding prose is the executor's to write within the "must say" and "must not say" lists.
Where a task gives text verbatim (fixtures, templates, the evidence reference, the README row, the fresh-session brief), the wording is itself the decision and is copied exactly.
Set the run date once per run task with `d=$(date +%F)` and reuse it for every path in that task.

**Fresh-session brief.**
Tasks 10, 11, and 13 hand the audit to a fresh session: a new model session with no conversation history, given no path to and no content from this plan, started with a working directory outside this repository's `docs/` tree.
